# 评价与阅读检查

按[工作流](workflow.md#试作到完整作品)选择当前评审范围。以下维度合并到同一次阅读与操作检查中，不必逐节另开一轮检查或生成总分。沿实际阅读路径观察，能连续完成的操作一并做；截图用于判断构图，结构或读数查询用于定位问题，不机械地对每一步都重复两套观察。

| 维度 | 判断问题 | 可用的观察方式 |
| --- | --- | --- |
| 证据 | 主发现由什么支持，比较口径能否成立？ | 重算关键结果，抽查原始来源、缺失与分母 |
| 叙事 | 是否回应用户关注的问题，主线、必要背景与补充是否各得其所？ | 连续阅读各段，复述证据如何接起追问；辨认重复解释和缺少承接的分支 |
| 可见证据 | 正文强调的差异、结构或变化能否在图里指出？ | 暂时遮住长段解释，只看图形和必要标签 |
| 编码与身份 | 标记、尺度和对应是否清楚，是否暗示不存在的流向？ | 检查端点、面积、成员变更和图例；追踪一个代表对象 |
| 构图与艺术 | 当前问题的核心证据是否获得足够空间，素材与辅助视图各提供什么帮助？ | 对照正在读的文字辨认主视觉，观察局部是否拥挤而背景占据主要空间；用真实极值与长标签看完整构图 |
| 节奏与连续 | 相邻段落、图形和素材是否共同接续，发展变化是否留有可比较的参照？ | 连读普通图文与舞台的交接；动态部分看完整画面的停滚、反向、直接导航和快速跳转 |
| 探索（如有） | 简洁操作能否回答一个值得追问的问题，选择与结果是否清楚一致？ | 从默认状态做一次主要操作，连同焦点、选中和实际出现的展开状态观察控件与作品是否协调、有无遮挡；再检查空结果与返回主线 |

新颖不是单独的胜出条件。常规编码若能明确回答问题，可以与更有表现力的段落共存；复杂机制需要给读者带来额外理解或明确的主题体验。

## 开篇与首个数据画面的阅读检查

从开篇沿实际阅读路径进入第一项数据发现；若开篇已经承担证据作用，就继续到下一项发现。按[开篇设计](narrative-design.md#开篇的选择与交接)中的意图观察：

- **对象与期待：** 读者能否说出在讲什么、为什么值得继续，以及接下来希望弄清什么？只认出标题或觉得图片漂亮，还不足以说明引入成立。
- **理解负担：** 在尚未读后文时，能否识别当前重点？已出现的数据标记是否有足够的身份、单位与编码说明？哪些轴、图例或导航现在就有用途，哪些到后文才需要？仅负责情境引入的画面无需提前讲解整套图例；直接用数据开篇则应已能读出一个关系。
- **证据承接：** 下一画面是否提供回应开篇期待的证据？能否指出延续的对象、参照或问题，以及新看清了什么？问题可以逐步回答，但第一步应让读者看见进展。

用这些阅读结果判断入口是否有效，图片数量、动画复杂度和是否单设封面都不是通过标准。

## 正文、图形与排版的共同阅读

按[交付范围](../SKILL.md)在桌面窗口连读全文，兼顾笔记本可用高度，一并观察正文、图形与实际显示的字体：

- **段落承接与信息分工：** 能否复述对象发生了什么、比较条件是什么，以及这一段为何接在这里？正文、标注与图注是否各有帮助，已建立的读法是否继续沿用？若主要读到制作过程或重复结论，按[正文编排](narrative-design.md#把段落写成可阅读的正文)调整信息位置、合并重复说明，保留影响判断的必要条件。
- **注意力对应：** 正文关键数字能否对应图中的对象与关系，画面最醒目的内容是否服务当前问题？按[图文对应](visualization-design.md#正文重点与图形证据)检查，区别“读数存在”和“关系容易看见”。
- **实际可读性：** 中文、英文、数字与单位的字形、层级和断行是否协调，有无缺字、重叠或裁切？素材的主体与边缘是否清楚，标签、素材与正文是否相互遮挡或难以辨认；有动画时也观察移动过程。需要调整时回到[素材与排版指导](material-direction.md)。

记录读起来断裂、找不到对应或难辨认的具体位置及修订结果。需要定位越界或遮挡时，可在这次检查中使用[占位测量与空间诊断](implementation-rendering.md#实际占位与空间诊断)，只检查构图指定的关系，再结合画面判断候选；无需新增检查轮次。句式是否整齐、是否用了某种字体、是否避开几个词，都不能代替实际阅读判断。

## 试作与交付

在交付说明或已有检查记录中，简记已检查的范围、具体问题及修复、未验证的部分，区分可计算事实、实际浏览器行为与编辑视觉判断。数据正确和运行正常不自动证明关系易懂，作者自查与真实读者反馈分别记录。来源与设计引用已有文件，设计稿只同步改变的决定；快照、哈希清单或额外验收文档按明确交付要求生成，普通创作无需附加。文件分工见[工作流](workflow.md#研究设计与验收各自记录什么)。

实现交付从实际输出目录按约定方式打开，确认样式、脚本、数据和素材随产物可用；需要时使用[预览与资源检查工具](implementation-delivery.md#静态交付与工具选择)。采用构建时检查生成物，避免仅验证开发服务。资源检查通过后，浏览器仍需沿真实阅读与操作路径观察；记录目标状态不能代替确认画面已经完成。已通过且输入未变的检查结果继续沿用；修订后复查受影响的画面和衔接，不从头重复整套流程。

发现问题后回到对应环节：画面本身不支持正文结论，调整叙事或构图；设计中的关系成立、成品却丢失对应或过程，则修正实现。试作后换过图形时，对照设计稿确认核心关系仍可见，而不只比较读数是否更清楚。保留具体位置、修订决定及仍未验证的部分，避免只记录笼统的“通过”。
